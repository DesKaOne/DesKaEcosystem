# Consensus Persistence → Canonical Commit Boundary v0.1\n\n## Purpose\nMilestone 4.47 defines the handoff contract between consensus/execution coordination and the canonical ChainStore commit boundary.\n\nThe contract closes the gap identified by milestone 4.46: persistence/recovery may produce a validated candidate, but canonical chain/state publication remains owned by the node/storage boundary.\n\n## Boundary\n```text\nConsensus / Recovery\n        |\n        | fully validated CanonicalCommitCandidate\n        v\nCommitCanonicalCandidate\n        |\n        | validate hash + state-root binding\n        v\nCanonicalCommitter\n        |\n        | CommitBlockState(...)\n        v\nChainStore\n        |\n        v\nCanonical block + state\n```\n\nCanonicalCommitter is intentionally a narrow interface matching the existing storage.ChainStore CommitBlockState method. This keeps consensus independent from the storage implementation while making the handoff explicit.\n\n## Candidate invariants\nA CanonicalCommitCandidate contains:\n- block\n- block hash\n- resulting state snapshot\n\nBefore the store is called:\n1. state must be non-nil;\n2. block hash must be non-zero;\n3. supplied hash must equal the deterministic block hash;\n4. when the block carries a non-zero state root, it must equal the candidate state root;\n5. validation must not mutate the candidate or canonical state.\n\n## Ordering contract\nThe canonical handoff is ordered as:\n1. consensus/recovery validates its own context and evidence;\n2. execution produces the candidate state;\n3. block hash/state-root binding is validated;\n4. CommitCanonicalCandidate calls CommitBlockState exactly once;\n5. only after a successful return may the caller publish/advance in-memory consensus or node state.\n\nA failed validation must not call the canonical store.\nA failed canonical commit must not be treated as successful consensus publication.\nThe coordination helper does not retry, resubmit, or mutate consensus runtime state.\n\n## Failure ownership\n| Failure | Owner | Required result |\n|---|---|---|\n| Invalid recovery evidence | consensus/recovery | no canonical commit |\n| Candidate hash mismatch | coordination boundary | no canonical commit |\n| Candidate state-root mismatch | coordination boundary | no canonical commit |\n| Store/commit error | canonical storage boundary | error returned; no success publication |\n| Runtime publication after commit | caller/node boundary | occurs only after successful commit |\n\nThe storage implementation remains responsible for its own durable atomicity guarantees. This milestone does not upgrade MemoryStore or FileStore into a transactional storage engine.\n\n## No-partial-publication invariant\nThe coordination layer follows a strict prepare/commit/publication separation:\n```text\nprepare candidate\n    |\nvalidate candidate\n    |\ncanonical commit\n    |---- error ---> return error; do not publish success\n    |\n  success\n    |\npublish/advance caller-owned runtime state\n```\n\nThe helper itself has no mutable consensus runtime state to publish. This is deliberate: it prevents the persistence adapter boundary from becoming a second canonical state machine.\n\n## Scope boundary\nThis milestone does not implement:\n- production WAL writer/reader;\n- snapshot persistence;\n- filesystem crash recovery;\n- fsync/durability policy;\n- transactional database semantics;\n- distributed recovery coordination;\n- automatic retry/resubmission;\n- canonical state mutation merely for tests;\n- production BFT completion.\n\n## Verification\ncanonical_commit_boundary_test.go covers:\n- valid candidate acceptance;\n- hash mismatch rejection;\n- state-root mismatch rejection;\n- validation-before-store ordering;\n- exactly-one store invocation on success;\n- commit failure propagation without success publication;\n- nil committer rejection.\n\nThe tests use an in-memory fake committer and do not activate production persistence.\n\n## Relationship to 4.46\n4.46 established that recovery can build a candidate and publish it atomically within the recovery harness.\n\n4.47 establishes the next boundary: recovery publication is not canonical chain/state commit. Canonical commit must cross the explicit CanonicalCommitter boundary first.\n\n## Known limitations\nThe existing ChainStore.CommitBlockState implementation remains the actual canonical storage atomicity boundary. This contract does not prove filesystem crash atomicity or process-level durability.\n\nA future persistence implementation must provide its own durable atomic commit semantics before canonical persistence is considered production-ready.
